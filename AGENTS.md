# AGENTS.md — kvuno-api

Flask (flask-openapi3) + SQLAlchemy + PostGIS API that ingests agricultural `.RDS`/`.parquet` files and serves crop planting data. Background ingestion via Celery/Redis. Python 3.14 in the images and CI (`requires-python >=3.13`), Poetry.

## Commands

```bash
poetry install                     # venv is in-project (.venv), see poetry.toml
poetry run ruff check .            # lint (CI gate; ruff defaults + T20: no print() anywhere)
poetry run pytest -v               # all tests
poetry run pytest tests/test_config.py -v      # single file
poetry run pytest -k build_db_url              # single test
poetry run pip-audit --strict      # CI also runs this; deps are security-gated
python run.py                      # dev server (dev console script: `poetry run dev`)
python dev_worker.py               # Celery worker, auto-picks --pool solo on Windows
python housekeeping.py [DIR] [--dry-run] [--watch/-w] [--batch-size N] [--chunk-size N] [--checkpoint-interval N]   # Typer CLI, no Celery
python scripts/convert_rds.py PATH... [--out-dir DIR] [--overwrite]   # RDS -> Parquet locally (rds_to_parquet.convert), to upload the Parquet
```

A root `Makefile` wraps these (`make help` lists targets; e.g. `make check`, `make dev`, `make migration MSG="..."`). Order that matters: `ruff check .` -> `pytest`. There is no typecheck step (pylint config in `.pylintrc` is not wired into CI).

## Environment quirks (high value)

- **All configuration is `Settings` in `app/config.py`** (pydantic-settings, the budget-assist pattern). Read it with `get_settings().NAME` — never `os.getenv` for an app setting, and never copy a setting into a module-level constant (it goes stale, and tests then have to patch each copy; there are deliberately no `MAX_FILE_SIZE`-style module names left). `get_settings()` re-validates only when a setting's env var changed, so tests just `monkeypatch.setenv` — do **not** `sys.modules.pop`/reload `app.config` (that created a second `ConfigurationError` class and broke `pytest.raises` elsewhere). Import validates nothing; the preflight, `create_app()`, `app/celery_app.py` and `app/gunicorn_config.py` call `get_settings()` and an invalid value is a `ConfigurationError` listing every problem (the preflight exits 1 without retrying and warns about unknown look-alikes such as `LOG_LEVLE`). `build_db_url()` raises when it finds neither `DB_URL` nor all of `DB_USER`/`DB_PASSWORD`/`DB_NAME` (sqlite excepted). Empty values mean "default" (`env_ignore_empty`). Rate-limit decorators take a callable (`lambda: get_settings().RATE_LIMIT_X`); limiter storage/defaults are applied in `configure_limiter(app)`. There is no `JWT_SECRET` — auth uses opaque tokens.
- ⚠️ **`.env.example` and the README "Configuration" tables are generated** by `scripts/gen_config_docs.py` (`make config-docs`); the Python CI job runs `--check` and fails on drift (`changed-areas` routes `README.md`/`.env.example` edits to it). Adding a setting = a field in `Settings` with `_f(default, group, description)` (`active=True` makes it a live line in `.env.example`, `secret=True` + `SecretStr` for credentials), then regenerate. Edit the README only outside the `<!-- config:start … config:end -->` block.
- **Postgres driver is psycopg3, not psycopg2.** `poetry.lock` pins SQLAlchemy 2.1.x, which flipped the default dialect: `postgresql://` (what `build_db_url()` produces) now resolves to `PGDialect_psycopg`, so the `psycopg` v3 package is required — without it the app dies on connect with `ModuleNotFoundError: No module named 'psycopg'`. `psycopg2-binary` is still declared but is now dead weight unless the URL is explicitly `postgresql+psycopg2://`. ⚠️ `psycopg` (not `psycopg[binary]`) loads **system libpq**, which `python:3.14-slim` does not have — a container needs `psycopg[binary]` or `libpq` installed.
- `DB_URL` wins over the individual `DB_*` vars. `DB_DRIVER=sqlite` + `DB_NAME=file.db` + `alembic upgrade head` (which now runs end-to-end on SQLite: `postgis` extension Postgres-only, inline unique constraints, `coordinates` as `Text`, `migration_utils.now_default()`) is enough for UI/auth work — but **ingestion and the spatial queries still need Postgres** (`postgresql.insert(...).on_conflict_do_nothing()`, `ST_*`). Postgres path uses `postgis/postgis:17-3.5`.
- Tests rely on `pytest-env` (`pyproject.toml [tool.pytest.ini_options]`) forcing `DB_URL=sqlite:///:memory:` so app imports don't hit real config. Test suite is **unit-only** — no DB, no Redis, no API-server fixture. If you add tests, don't assume an app context or client exists.
- The frontend is a **separate** Vite + React + TypeScript SPA in `frontend/`, with its own `package.json`/`pnpm-lock.yaml` and its own CI job. `pnpm run build` there runs `tsc -b` first, so a type error fails the build. ⚠️ pnpm 12 reads its settings from `frontend/pnpm-workspace.yaml`, **not** `package.json` (whose `"pnpm"` field it ignores with a warning): build-script approvals (`allowBuilds: esbuild` — without it `pnpm install` dies with `ERR_PNPM_IGNORED_BUILDS`) and `overrides` (the `@remix-run/router` security floor) both live there.

- **A startup preflight gates the API and worker, and it is a trap for the dev server.** `app/utils/preflight.py` checks the database (always) and Redis (always for the worker; for the API only when `HOUSEKEEPING_ENABLED=true`, since with housekeeping off progress goes to PostgreSQL and nothing is enqueued). It retries `PREFLIGHT_RETRIES` times `PREFLIGHT_DELAY_SECONDS` apart and then exits 1. `PREFLIGHT_ENABLED=false` skips it entirely. It runs from `docker/entrypoint.sh`, the new `docker/entrypoint.worker.sh` (the worker image used to run `celery` directly, so a missing broker idled forever), and `run.py`. ⚠️ `run.py` is the exception: with `FLASK_DEBUG=true` it **warns and starts anyway** — do not "fix" that into a hard exit, it blocks local dev when Postgres/Redis are not running. Containers must still hard-fail, which is why the entrypoint check is independent.
- ⚠️ `preflight.check_database` passes a **driver-specific** connect-timeout option: `connect_timeout` for Postgres/MySQL, nothing for SQLite. psycopg2's spelling is `timeout`, and psycopg3 rejects it with `invalid connection option "timeout"` — a *hard error*, not a timeout, so the check fails against a perfectly healthy database and the API refuses to boot. `tests/test_preflight.py` guards the mapping.
- **The Vite dev proxy target is easy to get wrong.** `frontend/vite.config.ts` proxies `/api`, `/ui`, `/health` to `VITE_DEV_PROXY_TARGET`, defaulting to `http://127.0.0.1:5000` (the compose `api` service publishes host 5000 → container 80). Point it at `http://127.0.0.1:80` when running `python run.py` directly. A mismatch appears as `http proxy error: /api/...` with `ECONNREFUSED` — the SPA loads but every call fails.

- **Job progress lives in `processing_runs` + `processing_jobs`, which replaced the old `job_progress` table.** `job_progress` had a UNIQUE constraint on `file_name`, so it held one row per filename *forever* and re-processing a file silently overwrote its history; it also had no `started_at`, so the rows/sec + ETA depended entirely on the Redis hash and vanished on any DB read. The new pair is keyed on `(run_id, file_name)`, adds `started_at`/`finished_at`/`error`/`attempts`/`worker`, and a run groups the files submitted together so a multi-file upload can be reported as a batch. ⚠️ `updated_at` is now written **explicitly** on every update — the old column relied on `server_default=now()`, which fires on INSERT only, so it kept the creation timestamp forever and made healthy jobs look stalled to `mark_stale()`. `tests/test_progress_store.py` guards all of this.
- Progress has **two write cadences**. Redis is the hot path the SSE stream reads (throttled by `JOB_PROGRESS_MIN_INTERVAL`), Postgres is the durable record (throttled by `JOB_DB_CHECKPOINT_SECONDS`, default 5s); terminal states always write through both. Previously an in-flight job was written to Postgres *only* when Redis was absent, so a broker restart lost every running job. A run's status is **derived from its jobs** in `list_runs()`, not read from `processing_runs.status` — nothing reliably calls `finish_run()`, so deriving it means a run cannot be left claiming to be running. Every enqueue (`process_file_async`: upload submit, Jobs Retry, `/api/v1/data/upload`) opens a `source='upload'` run and passes `run_id` to the task (discarded if the enqueue fails); a startup/CLI scan opens one `source='scan'` run for all its files; `attempts` counts on per file across runs.
- ⚠️ **Engines use `pool_pre_ping=True` and `pool_recycle=1800`** (`MyDb.ENGINE_OPTIONS`, applied in `MyDb.init_app`, so the API app and the worker's app both get them; explicit `SQLALCHEMY_ENGINE_OPTIONS` win). Without them a pooled connection that died while idle was handed out as live, the first query of a job failed, and `retry_db` retried on the same invalid session: "Database unavailable … Can't reconnect until invalid transaction is rolled back" at row 0. `retry_db(..., session=...)` now rolls back before each retry — pass the session **only** where nothing uncommitted is at stake (the checksum lookup before an ingest); mid-ingest a rollback would drop rows written since the last checkpoint while the offset moved on, so there the error propagates and the file resumes from its checkpoint. `tests/test_db_resilience.py`.
- ⚠️ **`progress_store` writes through its own short-lived `Session`** (`_db_session()`), never `MyDb`'s scoped session. Ingest holds uncommitted rows in the scoped session between checkpoints; a progress write that committed it committed those rows ahead of their offset, so a resume re-inserted them and logged spurious conflicts. Checkpoints commit rows **and** offset together (`upsert_offset(commit=False)` + one `session.commit()`). Naive-UTC DB timestamps go through `_epoch()` (treats naive as UTC) — `datetime.timestamp()` assumed local time and made jobs look stale on non-UTC hosts. `tests/test_ingest_pipeline.py` covers these.
- **Ingest concurrency + retries.** Celery uses `task_acks_late` + `task_reject_on_worker_lost=True` and `broker_transport_options.visibility_timeout = CELERY_VISIBILITY_TIMEOUT` (default 21600 s) — Redis redelivers an unacked task after that **even while it runs**, so it must exceed the longest single-file ingest. A per-file `<file>.ingest.lock` (`app/utils/file_lock.py`, O_EXCL, touched every chunk, stale after `INGEST_LOCK_STALE_SECONDS`=600) makes a second worker on the same file **return silently** (an error write would fail the live job). `process_file` re-raises only transient DB errors (`is_transient_db_error`) so `autoretry_for` resumes from the stored offset; a bad file is recorded as `error` at its last checkpoint row and **not** retried. Default/sidecar column maps are intersected with the file's columns (missing ones logged); an explicit upload map is not.
- ⚠️ **Worker restarts pause and resume ingests; they used to hang them.** Docker's SIGTERM reaches only Celery's main process (the ingest runs in a prefork child), so `worker_shutting_down` (`app/celery_app.py`) drops a stop file (`housekeeper.WORKER_STOP_FILE` in the temp dir) that `stop_requested()` checks **between chunks** — a chunk's rows and the offset after it commit together, the job stays `processing` with "Paused for a worker restart", the lock is released. `worker_init` clears the flag and `release_dead_locks()` (locks now record `"<hostname> <pid>"`; only this host's are removed), and `worker_ready` runs `resume_interrupted_jobs(worker_name())`: every job this host left `processing`/`stale` is re-enqueued **in its own run** (`process_file_async(run_id=...)` reuses, never discards) with the upload's saved map, like Retry. Compose gives the worker `stop_grace_period: 2m` (Docker's 10 s default killed it mid-file). After a hard kill the old unacked message is still redelivered after `CELERY_VISIBILITY_TIMEOUT`; `_already_reported_complete()` keeps it from overwriting the finished job with "Already ingested 0/0". Jobs are matched by hostname, so a worker that comes back under a different hostname does not pick them up (they go stale → Retry). `tests/test_worker_restart.py` covers this.
- ⚠️ **Signal handlers are CLI-only** (`install_signal_handlers()` from `housekeeper.run()`, which `housekeeping.py` — a Typer CLI — calls). They used to be installed at import of `housekeeper`, hijacking gunicorn's and Celery's SIGTERM in every process that imported it.
- ⚠️ **Where files are processed: never in a gunicorn worker.** Gunicorn replaces a worker every `MAX_REQUESTS` (the Upload page polls every 1.5 s), and imports used to run on a daemon thread inside one: each recycle killed the import, which resumed from its last checkpoint — 2M rows took 40+ hours. Now, when `housekeeper.celery_worker_available()` (HOUSEKEEPING_ENABLED, broker up, and a worker whose `active_queues` include `CELERY_TASK_DEFAULT_QUEUE` — another project's worker on the same Redis answers a ping too; cached 30 s) is true: upload **inspection** is `tasks.inspect_upload_task` (`uploads.ensure_inspection` → `_queue_inspection`, which marks the row `received` + progress stage `queued` *before* sending, so the worker's claim is never undone; polls re-queue only after `UPLOAD_INSPECT_STALE_SECONDS`), the **import** is `process_file_async` with the saved map, and an RDS sent to `/api/v1/data/upload` is converted by `process_file_task` (`tasks._convert`, shown as a Converting job) instead of in the request. Without a worker: inspection on an API thread as before, and the import in a **detached** `python -m app.services.ingest_runner <upload_id>` (`routes/uploads.py::_spawn_runner`, `start_new_session` / Windows `CREATE_NEW_PROCESS_GROUP|CREATE_NO_WINDOW` — not `DETACHED_PROCESS`, which died with STATUS_CONTROL_C_EXIT), which outlives the gunicorn worker and retries transient DB errors from the checkpoint. `app/worker_app.py::build_app` is the minimal app both use. The production stack's worker must run Celery (`HOUSEKEEPING_MODE` empty); `oneshot` left nothing consuming the queue. Tests: `TestWorkOffTheApi` (`tests/test_uploads.py`, whose fixture stubs `_spawn_runner`), `tests/test_worker_routing.py`. Data-folder files: `create_app()` → `housekeeper.start_startup_scan()`, **once per deployment** although `create_app()` runs in every gunicorn worker and on every `MAX_REQUESTS` recycle: with `HOUSEKEEPING_ENABLED` it calls `process_pending()` (Celery; Redis `SET NX` key expiring after `STARTUP_SCAN_COOLDOWN_SECONDS`, so the API never imports files itself), otherwise `run_startup_scan()` claims `<data dir>/.startup-scan` (FileLock, stale = the cooldown, heartbeat every 30 s, file left in place afterwards as the cooldown marker) and only that process scans. `STARTUP_SCAN=false` disables it, and `pytest-env` sets that so no test scans the real folder (`tests/test_startup_scan.py`). Concurrent scans (CLI, watcher, worker) are still safe because `rds_to_parquet.batch_convert()` takes a per-file `<file>.convert.lock` (others skip), writes `<name>.parquet.tmp` and `os.replace`s it, treats a vanished RDS as done and skips a bad file (two gunicorn workers used to race: `FileNotFoundError` on `os.remove`, scan aborted — `tests/test_rds_batch_convert.py`), and ingestion has its `.ingest.lock`. Only `/api/v1/data/upload` and Jobs retries of plain data-folder files go to Celery, and only with `HOUSEKEEPING_ENABLED=true`. The API container is capped at 2 GB in the proxy-tool stack (raised from 512 MB, which failed every RDS upload over ~3 MB) and a large RDS is read whole, so RDS uploads over ~12 MB still fail with the "more memory than the server allows" message (only without a worker — production's worker runs Celery and does all file reading, so the API's limit matters only as a fallback). The worker image runs `housekeeping.py` instead of Celery when `HOUSEKEEPING_MODE=oneshot|watch|dryrun` (`docker/entrypoint.worker.sh`; a `Settings` field so it is validated and documented); the preflight then requires the database but **not** Redis.

- ⚠️ **`MyDb` is ONE `SQLAlchemy` instance bound per app, not one per `init_app` call.** `app/tasks.py` builds its own Flask app for the Celery worker, so a process touching both the API app and the worker app used to orphan the first app's sessions — surfacing mid-job as `RuntimeError: The current Flask app is not registered with this 'SQLAlchemy' instance`. `MyDb.db` is now created once and `init_app`'d to each app, which flask-sqlalchemy 3.x supports; both apps keep working. Do not "simplify" `init_app` back to `SQLAlchemy(app)`.

- **SPA uploads are tus 1.0 (core + creation) in Flask, tracked by the `uploads` table**, which replaced resumable.js, `.chunks/`, and the per-upload `.meta.json`/`.map.json`/`.preview.json` sidecars (model `Upload`, migration `20261022120000_create_uploads_table.py`, revision `7b1d0c5e2a91`). Lifecycle: `receiving → received → inspecting → ready | failed → submitted → processing → completed | failed` (`processing` is listed by `GET /ui/uploads` and cannot be discarded; `process_file` writes `completed` — or `failed` on a non-transient error — through `uploads.mark_processed()` when the import ends, so a finished file stops showing as Processing. The SPA's `statusBadge` must handle every status, or the Upload page crashes on reload). Ids are server-issued `uuid4().hex`, regex-validated before becoming a path; rows carry `owner_id` and another user's id is a 404. Bytes go to `HOUSEKEEPING_DATA_DIR/uploads/<id>/data.part` (the file size *is* the tus offset), renamed to `<id>.<ext>` on the last byte. ⚠️ It is a **subdirectory on purpose**: `load_rds_to_db` ingests every file in the data-dir *root* with the default mapping, which used to ingest uploads before the user mapped them. Concurrent `PATCH`es are serialised by an O_EXCL `.lock` file (423, stale after 30s). HEAD, PATCH and the status GET are `limiter.exempt` — a large file is many requests. CORS exposes `Location`/`Upload-Offset`/`Upload-Length`/`Tus-Resumable`, without which a cross-origin tus client cannot read them. `tests/test_uploads.py` covers the flow.
- ⚠️ **Never `rmtree` upload directories at boot.** `create_app()::_cleanup_temp_files` runs on every gunicorn worker boot (every `max_requests` recycle and timeout); it used to wipe the chunk dir and that was the main cause of random upload failures. It now only removes uploads idle past `UPLOAD_ABANDON_AGE` (default `7d`, `30m`/`12h`/`1d`/`2w` like `CLEANUP_AGE`) and files of jobs completed longer than `CLEANUP_AGE` ago (it also used to append a second extension, so processed data files were never deleted).
- **An upload's `column_map` is used AS IS by the worker** (`process_file(column_map=...)`), not merged over `RDS_COLUMN_MAP` defaults — merging re-mapped columns the user skipped and made pyarrow fail on defaults absent from the file. Inspection seeds it via `suggest_column_map()` (exact name, then `COLUMN_ALIASES`, which now lives in `services/uploads.py`); "skip" deletes the key; `validate_column_map()` requires `lat` and `lon`, no target twice, sources in the file, targets in `planting_recommendations`. Jobs-page Retry posts only the file name to `/ui/process`, which re-uses the saved map (it used to send `{}` and wipe it). `/ui/process`'s path check is `Path.is_relative_to`, not a string prefix.
- ⚠️ **Never use `result.rowcount` for the ingest INSERT.** Under psycopg 3 it is -1 for `INSERT … ON CONFLICT DO NOTHING`; testing `rowcount < len(rows)` made every batch run the conflict lookup (full scan, ~45 min for 2M rows) and log every inserted row as a conflict. `_insert_statement()` RETURNs the key columns, executed as executemany (compiled once — the old `.values(rows)` was ~250 ms of compilation per batch); `_not_inserted()` diffs them as a multiset; `_existing_rows_query()` looks up only those, via the unique index. `lon`/`lat` are **`REAL`**: compare through `_key()`/`_as_real()` and cast parameters to `REAL`, or nothing matches and the index is skipped. `tests/test_ingest_conflicts.py`. Conflicts from the fixed code have `source='ingest'`; `'housekeeper'` rows are from the old code, mostly false, and `scripts/cleanup_conflicts.py` (dry run unless `--apply`; ids fixed in a temp table first, or batched deletes would renumber each group and eat it) removes the false ones — self-clashing (`check_sum` = `record_data->>'check_sum'`), first per (file, key) — keeping cross-file and real in-file duplicates. The unused `PlantingRecommendationRepo.batch_insert` (same rowcount bug) was deleted; migration `d9f1b3c5e7a2` drops the second GiST index `idx_planting_recommendations_coordinates`. `resume_interrupted_jobs` also resumes **stale** jobs from any host (the API's old thread imports), not only this host's. Measured on `postgis/postgis:17-3.5`: ~14k rows/s clean, ~6k rows/s at 50% duplicates with logging.
- **RDS → Parquet conversion reports progress.** `_convert_in_child` uses `Popen` + a stdout reader thread: the child prints `read <rows>` / `write <done> <total>` (Parquet written in slices via `ParquetWriter`), the parent calls `on_progress(stage, done, total, elapsed)` on each line and every `PROGRESS_TICK_SECONDS` while pyreadr is silent; a raising callback never fails the conversion. Uploads write it to `uploads.progress` (`_ProgressWriter`, own Session, ≤ every 2 s unless the stage changes, cleared when inspection ends; `to_dict` exposes it only while `inspecting`). Scans (`batch_convert(on_file=report_conversion)`) and the watcher write a Jobs-page job under the RDS name with status `converting` → `completed`/`error`; `mark_stale` covers `converting`. ⚠️ `tests/test_uploads.py` patches `threading.Thread` **globally** — its `_InlineThread` starts named non-inspection threads for real, or the converter's reader never runs and the test hangs.
- **Data-folder files the defaults cannot map are held, not imported.** `housekeeper.hold_unmapped()` (scan, before `start_run`, and the watcher) checks a Parquet file's footer columns against `load_column_map()`; no `lat`+`lon` → `uploads.hold_from_folder()` moves it to `uploads/<id>/` as an `uploads` row with `source='folder'` (migration `b7d3f1a9c2e4`), `owner_id` NULL, inspected synchronously. Folder rows are visible to every signed-in user (`_visible_to`), counted by `GET /ui/uploads/awaiting` (sidebar badge on Upload), discardable only by an admin (403), and never removed by `cleanup_abandoned`. RDS is not checked (would be a full read). Toggles: `INGEST_HOLD_UNMAPPED`, `INGEST_DUPLICATE_CHECK` (off: `describe_duplicate` returns None and `process_file` re-imports a completed file from row 0), `INGEST_CONFLICT_LOGGING` (off: no `_log_batch_conflicts`; duplicates are still not inserted). Set them identically on API and worker — the API imports uploads, the worker scans. The Upload page processes only **opened** awaiting files.
- **`planting_recommendations.created_at` is the data date, `updated_at` the import time** — both always set by `housekeeper._row_mapping`. ⚠️ `model_dump()` carries them as `None`, and an explicit NULL overrides the `now()` server default: rows used to be stored with **no timestamps**. RDS and Parquet record no creation date (an RDS header is only format, R version and encoding), and file mtimes change on every edit or copy, so `created_at` comes from: the upload's **`data_date`**, confirmed on the mapping form (`POST /ui/uploads/<id>/process` `data_date`, `YYYY-MM-DD`, 1990..today, `''` clears; pre-filled from `uploads.file_modified_at` = the browser's `File.lastModified` sent as tus metadata `lastModified`, or a held folder file's mtime — `rds_to_parquet.keep_mtime` keeps the RDS's time on the Parquet for that), carried as `process_file(created_at=...)` through Celery (`created_at` ISO kwarg), the `ingest_runner` and `resume_interrupted_jobs`; otherwise the file's **first import time** (`file_imports.processed_at`, written once), so resumes and re-imports keep the same date. Migration `e2a4c6b8d0f1`.
- **A completed file stores `offset=None` in `file_imports`**; that is what every "already processed" check tests. It used to store `num_rows`, so dedupe never recognised a finished file — a legacy `offset >= rows` is now treated as processed and normalised. Also in `housekeeper.process_file`: `lat`/`lon` of `0` no longer null the coordinates (`is not None`, not truthiness — the NULL failed whole batches); on exception the session is rolled back and the error is reported at the last checkpoint row (where a retry resumes); an already-ingested file writes a `completed` progress entry instead of returning silently; completion with failed batches is `completed` with an error note.

## Architecture

- `app/__init__.py::create_app()` is the only wiring point: builds the `OpenAPI` app (`doc_prefix="/api-docs"`), CORS, rate limiter, error handlers, security headers, DB, then registers API blueprints + `app/routes/main.py`. `run.py` pushes an app context at import time — anything importing `run` gets one.
- API layer uses **flask-openapi3 `APIBlueprint`s**, not Flask blueprints. `app/api/planting_data.py` intentionally splits into `public_api` and `protected_api` sharing the same `url_prefix` (`/api/v1/planting-data`); only `protected_api` carries the JWT `abp_security`. Both are registered in `register_apis`. ⚠️ **`abp_security` only labels the OpenAPI doc — it enforces nothing.** Every protected view needs `@require_auth` itself; `/api/v1/quality/*` carried `abp_security` alone and was open until it got the decorator.
- API error contract: a caught exception is `logger.exception(...)`'d and the client gets a generic `{'error': ...}, 500` — never `str(e)`. Request validation failures are **422** (flask-openapi3's validation status, app-wide), including `sort_col`/`sort_dir`, which are whitelisted in `app/dto/data_filters.py` (`PLANTING_SORT_COLUMNS`, `CONFLICT_SORT_COLUMNS`) — they used to reach `getattr(Model, ...)` unchecked. Hand-parsed params (`/clusters` `zoom`/bounds) return 400. `/clusters` `pages` comes from `total_clusters` (cluster count), not the point total. `radius` is **metres**: the repo casts both sides to `Geography` before `ST_DWithin` (on SRID 4326 geometry it was degrees).
- `@api_cache` stores only **2xx `dict`/`list`** bodies (it replays without the status, so a cached 500 became a 200 for the TTL). After any change to `planting_recommendations` call `invalidate_planting_data_cache()` (`app/cache.py`, prefixes `filters`/`coordinates`/`coordinates_bulk`/`clusters`) — not `invalidate_cache('coordinates')`, which does not match `coordinates_bulk`. The API upload and the worker's file completion both call it; add any new cached planting-data prefix to `PLANTING_DATA_CACHE_PREFIXES`.
- `app/routes/main.py::register_app_routes` holds `/health` and the `/ui/*` **JSON** endpoints the SPA needs: `/ui/columns` (also returns `max_file_size`), `/ui/jobs/data`, `/ui/jobs/runs`, `/ui/jobs/events` (SSE), `/ui/progress/<file>`, `/ui/process` (Jobs Retry; omit `column_map` to re-use the saved one), `DELETE /ui/jobs/<file>` (**`@require_admin`**, `services/file_deletion.py`: deletes the stored file — an upload's whole `uploads/<id>/`, or a data-folder file with its `.map.json` — the `uploads` row, every `processing_jobs` row and the Redis entry for it, and runs left empty; **keeps** imported `planting_recommendations` rows and `file_imports`, so a re-upload is still a known duplicate; 409 while the job is `processing`/`converting` or a live process holds its ingest lock, which the delete holds itself meanwhile; `tests/test_file_deletion.py`). It calls `app/routes/uploads.py::register_upload_routes` for the tus server and upload lifecycle: `POST /ui/uploads/tus`, `HEAD`/`PATCH /ui/uploads/tus/<id>`, `GET /ui/uploads`, `GET`/`DELETE /ui/uploads/<id>`, `POST /ui/uploads/<id>/process`. There are **no server-rendered app pages** — the Jinja templates and `app/static/js/` were deleted in favour of the React SPA and `render_template` is not imported. The one HTML response is `/` for a browser (`Accept` containing `text/html`): a self-contained landing page (`app/routes/dashboard.py`, inline CSS, no script, no DB call) linking `SPA_ROOT_URL`, `/api-docs/swagger`, `/api-docs/openapi.json` and `/health`; `SPA_ROOT_URL` is only linked if it is an http(s) URL or a same-site path. Non-browser clients (`*/*`) still get a 302 to `SPA_ROOT_URL`, or a JSON pointer when it is unset (`tests/test_security.py`, `tests/test_dashboard.py`). `pytest-env` forces `HOUSEKEEPING_ENABLED=false`, so a developer `.env` with it on no longer makes every `create_app()` in the suite wait on Redis. ⚠️ The `/ui/*` naming is now a misnomer: those are APIs, not pages, and they return JSON.
- The SPA is served by its own nginx container, not Flask. `frontend/nginx.conf` serves the hashed bundle and reverse-proxies `/api`, `/ui`, and `/health` to the `api` service, so production is **same-origin** and CORS is unused there; `CORS_ORIGINS` only matters for `pnpm dev` on `:5173`. If you add a new endpoint the SPA must reach, it has to be allowed through nginx as well as registered in Flask — a route that exists in Flask but is not proxied returns the SPA's `index.html` instead of JSON.
- Layering: `api/` (HTTP) -> `repo/` (queries) -> `models/kvuno.py` (ORM, GeoAlchemy2). `dto/` holds Pydantic request/response models, including all filter validation. `services/` holds ingestion logic (`housekeeper.py`, `progress_store.py`, `uploads.py`, `watch_handler.py`); `tasks.py` is a thin Celery wrapper that builds its own Flask app + `MyDb` for app context — it does **not** import `create_app`.
- Auth: `app/auth.py::require_auth` accepts `Authorization: Bearer {id}|{secret}` or a `token` cookie; browsers get redirected to `SPA_LOGIN_PATH` (default `/login`, a **client-side** SPA route — the SPA reads `?next=` and returns there after sign-in), API clients get 401 JSON. Any new protected API must use it (or `@require_admin` for administrator-only views, as all of `/api/v1/admin/*` do). The token is stored in `localStorage` under `token` and mirrored to a cookie (`Secure` on https); the SPA reuses that key, so sessions survived the migration. A 401 from any SPA API call dispatches `kvuno:unauthorized` (`frontend/src/api.ts`), and the single `AuthProvider` drops the token so `RequireAuth` redirects to `/login?next=`. `POST /api/v1/users/logout` accepts the bearer header or the `token` cookie (its decorator used to sit on the pydantic model, so it 500'd).
- **Registration is open; administrator approval is the gate.** `REGISTRATION_ALLOWED_DOMAINS` is gone (no longer read — `app/config.py` says so; don't reintroduce it). `users` has `status` (`pending|approved|rejected|disabled`), `role` (`user|admin`), `reviewed_at`, `reviewed_by` (migrations `a8c4e2f1d9b3` — status/reviewed, `batch_alter_table` for SQLite — then `e16b8fad5988` — role). ⚠️ `status` has `server_default='approved'` (backfills existing accounts so the upgrade locks nobody out) but ORM `default='pending'`; `register` sets it explicitly — `pending`, or `approved` for an `ADMIN_EMAILS` address. Owners = `config.admin_emails()` (read per call); `is_admin` = owner or `role=='admin'`; `is_active` = owner or `approved` — a disabled role-admin **is** locked out, an owner never is. Login checks the password first (`401`), then `403 {msg, status}` for an inactive account, so status never leaks without the password. `_resolve_token` returns `None` for an inactive user, so their tokens die at once (`401`) without being deleted; disable/reject in `app/api/admin.py` also delete them. `require_admin` (`app/auth.py`) is 401 unauthenticated / 403 non-admin. Admin rules: owners and your own account are `400`; transitions approve ← pending/rejected/disabled, reject ← pending, disable ← approved, role only on approved, else `409`. `app/services/mailer.py` is stdlib `smtplib` on a daemon thread, never raises, and with `SMTP_HOST` or `MAIL_FROM` unset only logs `"email not sent: SMTP_HOST/MAIL_FROM unset" (logged with user ids, never addresses)`; links need an absolute http(s) `SPA_ROOT_URL`. The SPA's `/admin/users` sits behind `RequireAdmin` (waits for `me`, else `/jobs`); `AuthContext` re-fetches `/api/v1/users/me` on every token change. `tests/test_user_approval.py` covers it. Passwords > 72 UTF-8 bytes are a 422 at register and a 401 at login — bcrypt 5 raises `ValueError` on them. Token timestamps are **naive UTC** everywhere (`_utcnow()`/`_as_naive_utc()` in `app/api/user.py`; aware vs naive comparison 500'd every expiring token; `user_tokens.created_at` is bound as a parameter, not SQL `now()`, which SQLite lacks), and `last_used_at` is written only when unset or > 5 min old.
- Ingestion is resumable: SHA-256 checksum dedupe in `file_imports`, per-file `offset` checkpoints, batch inserts in savepoints. Don't restructure the row-commit/offset-persist order in `services/housekeeper.py` without reading it fully.

## Database / migrations

- Alembic `sqlalchemy.url = %(DB_URL)s`; `alembic/env.py` injects `build_db_url()` at runtime, so no URL is ever hardcoded.
- After changing `app/models/kvuno.py`: `alembic revision --autogenerate -m "..."`, then **edit the generated file by hand** — env.py's `include_object` already skips PostGIS bookkeeping tables, but SQLite vs Postgres need manual branches via `app/utils/migration_utils.py` (`get_integer_column_type()` returns `Integer` on SQLite, `BigInteger` elsewhere).
- **Migrations run from the container entrypoint, not from `create_app()`.** `docker/entrypoint.sh` calls `scripts/run_migrations.py` before the API starts, gated on `RUN_MIGRATIONS` (entrypoint default true; `docker-compose.yml` overrides it to `${RUN_MIGRATIONS:-false}`, so under compose migrate manually or set it). Outside Docker, run `alembic upgrade head` yourself or the app will 500 on missing tables. `run_migrations()` (`app/__init__.py`) is a no-op when the DB is unreachable, so a slow-starting database does not block boot. The worker image's `docker/entrypoint.worker.sh` only runs the preflight (`scripts/preflight.py worker`) and never migrates — it only receives work from the already-migrated API. ⚠️ `autoretry_for=(Exception,)` no longer covers a pre-migration task: `process_file` swallows non-transient errors (a missing table included), so migrate before starting the worker.
- Migration `f3a9c2d4e5b6` (`20261022130000_planting_unique_nulls_not_distinct.py`) **deletes data**: on Postgres ≥ 15 it removes NULL-aware duplicates on the 7 `uq_planting_recommendation` columns (keeps lowest `id`; downgrade does not restore them) and recreates the constraint `UNIQUE NULLS NOT DISTINCT`; no-op on SQLite / PG < 15. Conflict logging matches with `is_not_distinct_from` to agree with it.
- `python model-generator.py` regenerates `app/models/kvuno.py` from a live DB via `sqlacodegen` (**it truncates the file to a dummy comment first**, so it destroys hand-written models — only run it deliberately, with a clean git tree).

## Docker

`docker-compose.yml` defines `base`, `api` (prod image, gunicorn, `FLASK_DEBUG` default false), `api-dev` (dev image, `run.py`, host 5002, only with `--profile dev`), `web` (host 5001), and `worker` (has a `celery inspect ping` healthcheck); api/web/worker are `restart: unless-stopped`. Postgres/PostGIS and Redis are **not** compose services anymore, so only `web` declares `depends_on` (on `api` healthy), `DB_HOST` is required (`${DB_HOST:?...}`, no default) and `DB_HOST`/`CELERY_BROKER_URL` must point at externally running instances. All Dockerfiles live in `docker/`; `docker-compose.yml` and `.dockerignore` stay at the repo root because the build context is the repo root. Images: `docker/Dockerfile` (dev), `docker/Dockerfile.prod.dockerfile` (prod), `docker/Dockerfile.worker`.

**Container registry is GHCR, not Docker Hub.** Images are `ghcr.io/cgiar-agwise/kvuno-api`, `ghcr.io/cgiar-agwise/kvuno-worker`, and `ghcr.io/cgiar-agwise/kvuno-web`. `docker-build.yml` passes the full `ghcr.io/...` path as `image_name`; the reusable workflow logs in with the built-in `GITHUB_TOKEN` (`permissions: packages: write`), so there are no `DOCKER_USERNAME`/`DOCKER_PASSWORD` secrets. If you add an image, use the full registry path and keep the `permissions` block on every calling job. Build cache tags (`<image>:cache-<branch>`) are also stored in GHCR.

⚠️ **The CI/image pipeline is tuned to save CI minutes and has traps; read `docs/DEPLOYMENT.md` §9 before touching it.**
- `pr-checks.yml` (`UnitTests`) starts with a `changes` job (`.github/actions/changed-areas`, GitHub compare API, no clone) and runs only the affected jobs: one Python job (ruff + pip-audit + pytest, 3.14 only, one install), frontend, and on PRs a no-push Docker build of only the images whose *build inputs* changed. Drafts run nothing; PR runs cancel superseded runs. If you add a top-level path the images or tests depend on, check its classification in `changed-areas` (unknown files default to rebuilding the Python images). Renamed jobs mean branch-protection required checks must be updated.
- `docker-build.yml` builds `develop` only from a *successful push* run of `UnitTests` (`workflow_run.conclusion` and `.event` both checked — PR runs would publish fork code with `packages: write`), so `pr-checks.yml` **must** keep its `develop`/`main` push trigger. Develop rebuilds only images whose contents changed (push `before` from the repo activity API; unknown → build all) — a change to `docker-build*.yml` or `changed-areas` counts as an image change, otherwise a CI-only push (e.g. a pipeline fix) rebuilt nothing. The `workflow_run` triggers carry `branches:` filters (develop for docker-build, main for version-release) so other branches create no skipped runs.
- `main` is built **once**: `version-release.yml` runs on the successful `UnitTests` `workflow_run` for `main`, tags `workflow_run.head_sha` (`commit_sha`, and `release_branches: ".*"` because `GITHUB_REF` under `workflow_run` is the default branch), then *calls* `docker-build.yml` — a `GITHUB_TOKEN` tag never triggers workflows. A called workflow sees its caller's event, so `docker-build` tests `inputs.tag` before `github.event_name`. Only hand-pushed tags poll the `gate` (`wait-for-checks`, `sha` input).
- `docker-build-reusable.yml` takes tag *names* and prefixes each with the image (an unprefixed comma list made Docker Hub refs) plus a `context` input (`frontend` for web). Tags: develop → `:develop`; release → `:latest`, `:<tag>`, `:production`; all → `:sha-<short>`. Do not reintroduce a "skip if source unchanged" cache (it made release builds skip). Keep actions on version tags, not SHAs.

## Conventions

- Commits are Conventional Commits (`feat:`, `fix:`, `docs:`, `chore:`, `test:`), lowercase, short imperative subject. Match that.
- Rate limits come from `RATE_LIMIT_*` env vars in flask-limiter syntax (`"10 per hour"`, not bare ints) — the README's integer table is outdated.
- **Logging follows the budget-assist service: structlog over stdlib `logging`**, set up once by `app/utils/logging.py::setup_logging()` (called by `create_app()`, and from Celery's `setup_logging` signal so the worker does not hijack the root logger). Use `logger = get_logger(__name__)` and `logger.info("message", key=value)`; use `logger.exception` in an `except` that does not re-raise (re-raising repos log `error` only — the caller logs the traceback). `ENVIRONMENT=production|prod` → JSON lines, else console; `LOG_LEVEL`; `LOG_DESTINATION=stdout|stderr|file` (+ `LOG_FILE_PATH`, `LOG_ROTATION=size|daily`, `LOG_MAX_BYTES`, `LOG_BACKUP_COUNT`) — keep stdout in containers. All stdlib loggers (Flask, Werkzeug, SQLAlchemy, Celery) render through the same handler with the same fields (`foreign_pre_chain`). Context via `structlog.contextvars`: every API request binds `request_id`/`method`/`path` (from `X-Request-ID`, which kvuno-web's nginx sets from `$request_id`; validated, else a uuid) and returns `X-Request-ID`; a 500 body includes `request_id`; Celery tasks bind `task_id`/`task`. `emit_event()` (ingest telemetry) is a structured log call, not a print. loguru is gone (model-generator too). Repo per-query lines are DEBUG. **`LOG_LEVEL` is the only level** — the worker CMD and `dev_worker.py` pass it as `--loglevel` (there is no `CELERY_LOGLEVEL`), gunicorn reads it, and `alembic/env.py` calls `setup_logging()` instead of `fileConfig(alembic.ini)` (which reset the root logger to WARN and disabled ours). `DEBUG_DB=true` turns on the `sqlalchemy.engine` logger through the shared handler; `SQLALCHEMY_ECHO` stays False (echo adds its own handler that bypasses format and level). **No `print()`** — ruff `T20` (`[tool.ruff.lint]` in pyproject) fails CI on one. ⚠️ **No personal data in logs (IITA data rules):** identify people by id (`user_id`, `actor_id`, `about_user_id`), never email addresses or usernames; the mailer logs a `log_ref` of ids plus subject/recipient count, and an SMTP failure logs only the exception class and `smtp_code` (SMTP error text quotes addresses). `tests/test_user_approval.py::TestNoPersonalDataInLogs` guards this.
- Docs live in `README.md` plus `docs/` (DESIGN = UI/UX audit + routes, DATA-FLOW = ingestion/serving/schema, DEPLOYMENT = compose + images). Verify against code before trusting them — several details have drifted. The former SECURITY / IMPLEMENTATION / PERFORMANCE_IMPROVEMENT files were deleted once their task lists were fully complete; security controls are summarised in the "Existing Security Controls" table of git history and enforced in code (`app/auth.py`, `app/rate_limit.py`, `app/utils/downloader.py` SSRF guards).
- **The app version is never hardcoded.** `app/config.py` reads `APP_VERSION`, falling back to `GITHUB_REF_NAME` then `0.0.0-dev`. The Dockerfiles declare `ARG APP_VERSION` in the runtime stage and the reusable workflow passes it as a build arg, so `/health` and the OpenAPI `Info` block report the tag that was built. `version-release.yml` derives the tag from git history via `masgeek/github-tag-action`, which has **no** `version_file` input — the tag is the source of truth, so `pyproject.toml`'s `version` is cosmetic only (the project is `package-mode = false` and is never published).
- `HOUSEKEEPING_ENABLED=false` (default) runs the whole app without Redis/Celery: SPA uploads are received, inspected **and processed** in the API, and the startup scan imports the data folder. It only gates the Celery path (`/api/v1/data/upload`, Jobs retries of plain files) and the API preflight's Redis requirement; with it `true`, `process_file_async`/`_enqueue_or_warn` return `bool` and an unreachable broker is reported instead of claiming "Processing started".
- **Rate limiting has a blanket default that also covered static assets.** `app/rate_limit.py` sets `default_limits` (now 600/hour, 5000/day, overridable via `RATE_LIMIT_DEFAULT_HOURLY` / `RATE_LIMIT_DEFAULT_DAILY`) which applies to any route without its own limit. `limiter.exempt(app.send_static_file)` is set in `create_app()` — without it a single page view costs ~5 requests and the old `50 per hour` default was exhausted after ~10 views. If legitimate users see 429s, raise the default, not the per-endpoint limits.
- `PROXY_FIX_HOPS` (default **1**) wraps the app in werkzeug `ProxyFix` so `get_remote_address()` returns the real client rather than the reverse proxy. It is 1 because the `web` nginx container is the documented path in front of the API, and at 0 every user shared one rate-limit bucket. ⚠️ The tradeoff is real: `ProxyFix` trusts the header unconditionally, so an app exposed with **no** proxy in front can be rate-limit-evaded by forging `X-Forwarded-For` — set it to `0` in that case, notably when running `python run.py` straight onto a public port. Count the proxies in front of the app (2 if a CDN also sits in front). `tests/test_proxy_fix.py` guards both directions.
- `RATE_LIMIT_STORAGE` defaults to `memory://`, which is per-process: with multiple gunicorn workers the counters are inconsistent and a client can slip through by landing on another worker. Point it at Redis (already required for Celery) for shared counters. It is applied by the `Limiter` constructor, not after `init_app`.
- The explore table uses **paged navigation on purpose** — do not replace it with infinite scroll. Rationale in `docs/DESIGN.md`.
- **Upload inspection is off the request path and is where RDS becomes Parquet.** `pyreadr.read_r()` deserialises the *whole* file, so previewing 5 rows costs a full load; that is why it no longer happens inside a request. `services/uploads.py::inspect` runs as `tasks.inspect_upload_task` on the Celery worker when one consumes our queue, otherwise on a daemon thread in the API process (works with `HOUSEKEEPING_ENABLED=false`): `convert_for_ingestion()` (writes `.parquet`, deletes the `.RDS`). ⚠️ **The RDS read runs in a child process** (`rds_to_parquet._convert_in_child`, an inline script importing only pyreadr/pandas; also used by `batch_convert`): a 7.4 MB AgWise RDS (2.1 M rows) peaks at **~1.1 GB** while `pyreadr` reads it, which in the 512 MB API container got the gunicorn worker OOM-killed, the stale-inspection recovery restarted it on the next poll, and the upload sat at "Reading the file…" forever. Now only the child dies: exit `-9`/`4` → `ConversionError` "needs more memory than the server allows" (upload `failed` with that message), `2` → "not a readable R data file", `3` (Parquet write failed) → the original RDS path is returned, timeout `CONVERT_TIMEOUT_SECONDS` (30 min). Never fall back to reading the RDS in-process after a read failure — that is the same OOM. The API needs memory headroom of ~150× the RDS size per concurrent conversion (or users upload Parquet); `tests/test_rds_conversion.py`, `build_preview(use_cache=False)`, SHA-256, `describe_duplicate()`, `suggest_column_map()`. Results go on the `uploads` row, not sidecars. The claim is a conditional `UPDATE` (never runs twice); a heartbeat bumps `updated_at` every 30s, and a row `inspecting` past `UPLOAD_INSPECT_STALE_SECONDS` (180) is re-claimed by the next `GET /ui/uploads/<id>` — that poll is the recovery path for a recycled gunicorn worker. The stored `file` is `<id>.parquet` even when `.rds` went in. `/api/v1/data/upload` sends an RDS to the worker as-is when there is one (converted in `process_file_task`); without a worker it still converts inline and reads columns in the request. `build_preview`'s `.preview.json` cache has no caller that enables it anymore.
- **`MAX_FILE_SIZE_MB` is enforced at tus creation**, from the declared `Upload-Length`, before any bytes land (413; bad extension 415). A `PATCH` body past the declared length is also 413. nginx has `client_max_body_size 0` on `/ui/`, so the API is the only cap; the SPA reads it from `/ui/columns` rather than hardcoding 20 MB.
- `pandas.read_parquet` has **no `nrows` argument** (it forwards kwargs to `pyarrow.read_table`, which rejects it). `app/utils/preview.py` uses `pyarrow.parquet.ParquetFile` directly: `.schema.names` for columns, `.iter_batches(batch_size=n)` for rows.
- The only JS dependency tree is `frontend/node_modules` (pnpm); the old root `node_modules/` is gone. **Build contexts:** the root `.dockerignore` (Python images) keeps the context to the app, migrations, scripts, entrypoints and Poetry files (~1 MB) — it excludes `frontend`, `**/node_modules`, `**/__pycache__` (a pattern without `**/` matches the root only), every `.venv*`, `data`, `logs`, `static` (the data folder; `static/.gitignore` keeps its contents out of git too) and `.env*`; `frontend/.dockerignore` excludes `node_modules`/`dist` from the web context. The web Dockerfile copies named files, **including `public/`** (it did not, so the image had no `favicon.ico`). Bootstrap, Bootstrap Icons, Leaflet, markercluster, and leaflet.heat are bundled from npm now; the tus upload client is in-house (`frontend/src/lib/tus.ts`, no dependency) and `resumablejs` was removed with the chunk upload; nothing loads from a CDN at runtime. React Router routes are `React.lazy`-split, so the Leaflet-heavy `/explore` bundle only loads on that page.

It builds with node and ships nginx + `dist/`, so node never reaches the runtime image. `docker-compose.yml` has a `web` service for it on `127.0.0.1:5001:80` — hardcoded; there is no `WEB_PORT` (every compose port binds loopback only). The compose `worker` reads `.env` like `api` (`env_file`); its `environment:` block holds only compose-specific values, so do not restate defaults there.

Image default `http://kvuno-api:80` (this repo's compose); the production stack (`D:\Dev\tools\proxy-tool\stacks\kvuno`, service `kvuno`, behind Caddy on 9800/9801) sets `API_UPSTREAM=http://kvuno:80`. nginx leaves `Host` as the upstream's own (an https upstream behind a router would route on it), sends `X-Forwarded-Host`, and trusts `X-Forwarded-For` only from private ranges (`set_real_ip_from`) so it can forward the real client to the API's one-hop `ProxyFix`.

- All three app Dockerfiles (`docker/Dockerfile`, `docker/Dockerfile.prod.dockerfile`, `docker/Dockerfile.worker`) start their builder stage with `ARG POETRY_VERSION=2.3.2` + `FROM ghcr.io/masgeek/python-3.14-poetry:${POETRY_VERSION} AS builder`. Poetry itself lives in the shared `docker/Dockerfile.base`, installed with the official installer into `POETRY_HOME=/opt/poetry` and version-checked in the same layer; the app Dockerfiles only run `poetry install`.
- The builder base is `ghcr.io/masgeek/python-3.14-poetry:2.3.2`, built from `docker/Dockerfile.base` — note it lives under the `masgeek` namespace while the app images are `ghcr.io/cgiar-agwise/*`. **CI does not build or push it**; build it locally with `docker compose build base` (optionally `docker push` it). Its `image:` tag in compose must exactly match the `${POETRY_VERSION}` the app Dockerfiles reference, or Docker tries to pull a nonexistent tag.
- **The Poetry version must match the one that generated `poetry.lock`** — different 2.x releases compute a different content-hash for `pyproject.toml` and the build aborts with "pyproject.toml changed significantly". There is no automated check for this, so bumping Poetry means editing **all** of: `docker/Dockerfile.base` (ARG), the three app Dockerfiles in `docker/` (ARG), `docker-compose.yml` (`base` service `image:` tag *and* build arg), and both `snok/install-poetry` steps in `.github/workflows/pr-checks.yml` (`version:`, lint and test jobs) — then regenerating the lock with that same Poetry and rebuilding the base. Miss one and the failure looks unrelated to Poetry.
- The builder stages copy `pyproject.toml poetry.lock README.md`. The lock is required (otherwise the build re-resolves every time and drifts from CI); `README.md` is required because `pyproject.toml` declares `readme = "README.md"` and Poetry validates it — hence the `!README.md` negation at the end of `.dockerignore`, which must stay *after* the `*.md` rule it overrides.
- ⚠️ **The data volume must be owned by the image's `app` user.** All three images run as non-root `app` with a **fixed uid/gid 1000** (`ARG UID/GID`; prod and worker used `useradd -r`, an arbitrary system id) and create `/app/static/data/uploads` owned by it, so a *new* volume inherits that ownership. An *existing* volume keeps its owner (production's `kvuno-data` was root-owned → `PermissionError: 'static/data/uploads'` on every tus create). Both compose files therefore run a one-shot root `data-init` service (`kvuno-data-init` in the proxy-tool stack) that `chown`s wrong-owner entries to `app:app` **by name** (so it matches whatever uid the pulled image uses), and `api`/`api-dev`/`worker` `depends_on` it with `service_completed_successfully`. In the app, an unwritable data dir is a `503` from tus create (not a 500) and a non-blocking `data directory` line in the preflight.
- The app listens on **port 80** in both images. `run.py` defaults `SERVER_PORT` to 80, and `app/gunicorn_config.py` defaults `BIND_PORT` to 80. Compose maps host `5000` → container `80` and adds `cap_add: [NET_BIND_SERVICE]`, because the containers run as non-root `app` and ports below 1024 are privileged on Linux.
- The prod image really loads that config: `CMD ["gunicorn", "-c", "app/gunicorn_config.py", "wsgi:app"]`. Gunicorn only auto-loads `gunicorn.conf.py` from the working directory, so without `-c` the `BIND_IP`/`BIND_PORT`/`WORKERS`/`THREADS`/`TIMEOUT`/`LOG_LEVEL` env vars in that file are inert. It defaults to `worker_class=gthread` (2 workers x 4 threads) because the SSE endpoint would otherwise exhaust the sync worker pool.
- Dev and prod use **separate** Dockerfiles: `docker/Dockerfile` (CMD `python3 run.py`) and `docker/Dockerfile.prod.dockerfile` (CMD gunicorn, adds HEALTHCHECK). They share `docker/entrypoint.sh`, which applies migrations then `exec`s the image CMD — there is no build or runtime mode variable.
- `.dockerignore` **must stay at the repo root**, not in `docker/` — Docker only reads it from the build-context root, and the context is the repo root. Moving it silently disables every rule, including the `!README.md` negation Poetry needs.
- **A job showing `processing` forever means the worker died, not that it is busy.** `progress_store.mark_stale()` downgrades any `processing` entry whose `mtime` is older than `JOB_STALE_AFTER_SECONDS` (default 1800) to `stale`, because a job nothing has written to in 30 minutes cannot be in progress. Terminal statuses are never touched — a completed job from last week is history, not a stuck job. Keys also carry a `JOB_PROGRESS_TTL_SECONDS` expiry (7 days), refreshed on every write, so a crashed run cannot leak entries. Stale jobs get a Retry button like failed ones.
- **Ingestion streams Parquet instead of loading it whole** (`_iter_parquet_chunks`); peak RSS measured ~3x lower on a 2M-row file (227 MB vs 358 MB). `HOUSEKEEPING_CHUNK_SIZE` does **not** control memory — it only sizes the insert batches. RDS still fully deserialises: `pyreadr.read_r` has no `chunksize` parameter, so that is unavoidable, which is why uploads are converted to Parquet during inspection. `del data` was replaced with a `gc.collect()` because pandas/pyarrow return memory to their own arenas, not the OS.
- Worker memory: `WORKER_MAX_MEMORY_PER_CHILD` is **MB** and `celery_app.py` multiplies it by 1024 — Celery counts KiB, so the old raw 2048 meant 2 MiB and every child was replaced after every task. It only replaces a child *after* a task; it never stops one. What kills a task is the container's memory limit: production saw `WorkerLostError … signal 9 (SIGKILL)` with `CELERY_CONCURRENCY=2` in the 2 GB worker, so the default (image CMD, `Settings`, stack) is **1** — raise concurrency only together with the worker's memory. ⚠️ A SIGKILLed import leaves its `.ingest.lock`; `FileLock` now takes over a lock whose holder is a **dead pid on this host** at once (`_holder_is_dead`, POSIX `os.kill(pid, 0)`; Windows assumes alive — `os.kill` there terminates). Before, the requeued task (`task_reject_on_worker_lost`) found the lock "held", skipped the file silently, and the job stalled until Retry. `tests/test_file_lock.py`.
- `app/utils/downloader.py` follows redirects **by hand** (max 5; each hop SSRF-checked; a cross-host hop uses a bare session, so neither `Authorization` nor the non-host-scoped cookies follow it), matches `REMOTE_RDS_ALLOWED_DOMAINS` exact-or-subdomain (not suffix), caps size at `REMOTE_RDS_MAX_BYTES` (1 GiB) while streaming, and re-checks the connected peer IP against DNS rebinding — best effort, skipped behind an HTTP(S) proxy. Never switch it back to `allow_redirects=True`.
